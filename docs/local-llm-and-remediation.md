# 로컬 LLM 실행과 진단·수정 경계

Robot Ops Agent의 현재 실행 기준은 노트북이다. 로봇은 주행과 조작, ROS 2 상태 생성을 담당하고, 노트북은 문서 인덱싱·검색·진단 근거 수집·로컬 모델 실행을 담당한다. 이 구성을 먼저 완성한 뒤 Raspberry Pi나 Jetson에서 같은 흐름을 실측한다.

## 실행 구성

```text
로봇 또는 시뮬레이터
└─ ROS 2 상태·로그·rosbag
              │ 조회 전용
              ▼
노트북
├─ Robot Ops Agent
│  ├─ Markdown 증분 인덱스와 SQLite
│  ├─ 키워드·벡터·하이브리드 검색
│  └─ 조회 전용 MCP와 감사 로그
├─ llama-server :8081
│  └─ Qwen3-Embedding-0.6B-Q8_0.gguf
└─ llama-server :8080
   └─ Qwen3-0.6B-Q8_0.gguf
```

두 모델은 역할이 다르다.

| 구성 요소 | 역할 | 현재 연결 상태 |
| --- | --- | --- |
| Qwen3-Embedding 0.6B Q8 | 문서와 질문을 1,024차원 벡터로 변환 | 인덱싱·벡터 검색에 연결하고 Vulkan 기준선 측정 |
| Qwen3 0.6B Q8 | 검색 근거를 입력받아 답변 생성 | 별도 벤치마크 하네스에서만 측정 |
| llama.cpp `llama-server` | GGUF 모델을 로컬 HTTP API로 제공 | 루프백 주소로 실행한 기준선 보유 |
| Robot Ops Agent | 검색·ROS 조회·평가·감사 | 생성 모델까지 묶은 사용자용 `ask` 루프는 미구현 |

모델과 llama.cpp 바이너리는 저장소에 넣지 않는다. 새 환경에서는 고정한 모델 revision과 SHA-256을 확인해 별도로 설치한다. 권장 위치는 다음과 같다.

```text
$HOME/.local/share/robot-ops-agent/
├─ runtimes/llama.cpp-b10549/
└─ models/
   ├─ Qwen3-Embedding-0.6B-Q8_0.gguf
   └─ Qwen3-0.6B-Q8_0.gguf
```

재현 기준은 다음 문서와 집계 파일에 고정돼 있다.

- 생성 모델과 CPU 조건: [로컬 CPU 기준선](benchmark-2026-08-28.md)
- 임베딩 모델과 Vulkan 조건: [의미 검색 개발 기준선](semantic-retrieval-2026-08-28.md)
- 원본 모델·런타임 revision과 해시: `evaluations/baselines/`

## 노트북을 먼저 사용하는 이유

현재 노트북에서는 임베딩 모델을 Vulkan으로 실행했을 때 공개 문서 11청크 처리가 CPU 65.05초에서 1.72초로 줄었다. 반면 생성 모델의 CPU 첫 실행 TTFT P50은 18.04초였고 서버 최대 RSS는 2,008.98 MiB였다. 개발 단계에서는 자원 여유와 관찰 도구가 있는 노트북에서 진단 흐름을 완성하고 모델·프롬프트·검색 실패를 고치는 편이 적합하다.

노트북에서 실행하면 `로컬 Robot Ops 진단`이라고 표현할 수 있다. 로봇 본체의 Raspberry Pi나 Jetson에서 ROS 2와 모델을 동시에 실행하고 지연·메모리·온도·스로틀링을 측정하기 전에는 `엣지 배포`라고 표현하지 않는다.

## 현재 가능한 진단

현재 구현은 진단에 필요한 근거를 모으는 단계다.

| 기능 | 상태 | 설명 |
| --- | --- | --- |
| 운용 문서·과거 장애 검색 | 가능 | 키워드·벡터·하이브리드 검색과 출처 경로 제공 |
| ROS 2 상태·로그 조회 | 가능 | 노드·토픽·서비스 목록, 토픽 한 건, rosbag 정보, 허용 로그 조회 |
| 알려진 장애와 현재 증상 연결 | 부분 가능 | 검색 결과와 생성 답변을 따로 평가했으나 하나의 진단 루프로 통합하지 않음 |
| 신뢰할 수 있는 자동 원인 확정 | 불가 | 0.6B 개발셋에서 모든 필수 개념을 맞힌 질문이 2/7에 그침 |
| 수정 방법 추천 | 미구현 | 근거·신뢰도·검증 절차를 포함한 수정안 형식이 필요 |
| 코드·설정 자동 변경 | 차단 | 현재 도구는 파일 쓰기 권한을 제공하지 않음 |
| 로봇 상태 변경 | 차단 | 토픽 발행, 서비스·액션 호출, 재시작, 임의 셸을 제공하지 않음 |

따라서 현재 단계의 정확한 설명은 `조회 전용 진단 근거 수집기`다. `자동 진단 에이전트`라고 부르려면 질문부터 근거 검색, ROS 2 추가 조회, 원인 후보, 출처, 다음 확인 항목까지 한 번에 실행하고 홀드아웃 장애에서 정확도를 검증해야 한다.

## 안전한 오류 수정 단계

오류 수정은 로봇 구동과 분리해 단계적으로 확장한다.

1. **관찰**: 문서·ROS 2 상태·로그·rosbag을 읽고 원본 근거를 보존한다.
2. **진단**: 원인 후보, 신뢰도, 반대 근거, 추가 확인 항목을 제시한다.
3. **수정안 생성**: 코드 diff나 YAML 변경안을 별도 산출물로 만들고 실제 파일에는 적용하지 않는다.
4. **격리 검증**: 테스트, 시뮬레이터, rosbag 재생으로 수정 전후를 비교한다.
5. **승인 후 반영**: 사람이 검토한 변경만 Git 브랜치에 적용한다. 실제 로봇 배포는 별도 절차로 둔다.

LLM이 `/cmd_vel`이나 관절 명령을 발행하는 경로는 만들지 않는다. 향후 제한된 복구 기능을 추가하더라도 고정 runbook, 명시적 승인, 사전 조건, 롤백, 감사 기록을 모두 갖춘 비구동 작업으로 한정한다.

## 구현 순서

다음 구현은 아래 순서로 진행한다.

1. 고정 release와 SHA-256을 검증하는 llama.cpp·GGUF 설치 절차를 재현한다.
2. `질문 → 검색 → 필요한 ROS 2 조회 → 근거가 있는 답변`을 묶은 로컬 `robot-ops ask` 흐름을 만든다.
3. 원인이 이미 확인된 장애 시나리오와 개발 과정에서 보지 않은 홀드아웃 질문으로 진단·출처 정확도를 평가한다.
4. 실제 적용 없이 diff와 검증 명령만 만드는 수정안 제안 단계를 추가한다.
5. 노트북 기준선을 통과한 뒤 Raspberry Pi나 Jetson에서 ROS 2 동시 실행 조건을 측정한다.
